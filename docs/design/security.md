# 権限と RLS の方針（Phase 0 案）

「見えない」は画面で隠すだけでなく、**DB（RLS）と API のレベルで取得できない**ようにする（要件 §3）。

## 1. 利用者の見分け方

| 利用者 | ログイン | DB 上の扱い |
|---|---|---|
| オーナー | Google またはメールのマジックリンク | `app_users.role = 'owner'` かつ有効 |
| 管理者 | 同上 | `app_users.role = 'manager'` かつ有効 |
| スタッフ | なし（マイページURL） | ログインしない利用者（`anon`）。**テーブルは一切直接読めない**。マイページ用の DB 関数だけを呼べる |

RLS の判定には次の関数を使う（`security definer`、`app_users` を毎回見るので、無効化は即時に効く）。

- `is_owner()` … 有効なオーナーか
- `is_member()` … 有効なオーナーまたは管理者か

> JWT（ログイン情報）に権限を埋め込む方式は、無効化しても最長1時間ログイン状態が残るため使わない。

## 2. テーブルごとの権限

| テーブル | オーナー | 管理者 | スタッフ（マイページ） |
|---|---|---|---|
| 現場・アサイン・実績・経費・スタッフ（金額以外）・会場・営業・マスタ・テンプレート | 読み書き | 読み書き | 直接は不可（関数経由で本人の分だけ） |
| `app_users`、`settings`、マスタ、テンプレート | 読み書き | 読むだけ | 不可 |
| ★ 金額系（下の一覧） | 読み書き | **不可（0件が返る）** | 不可 |
| ★ `audit_logs` | 読むだけ | 不可（実績の履歴だけ専用関数で見られる） | 不可 |
| `rate_limits` | 不可 | 不可 | 不可（関数だけが使う） |

**★ 金額系テーブル（オーナーのみ）**: `staff_private`（日当・源泉・インボイス・契約書・口座）、`rank_rates`（ランクごとの基準日当）、`assignment_private`、`company_billing`、`client_rates`、`event_rates`、`incentive_rates`、`event_incentive_rates`、`payment_adjustments`、`monthly_closings`、`closing_logs`、`payments`、`invoices`、`owner_settings`、`monthly_targets`、`audit_logs`

**例外**: 交通費・経費の申請額（`expenses.amount`）は、要件 §3 のとおり管理者も見て承認できる。

**削除**: 原則どのテーブルも削除の権限を与えない（無効化・アーカイブで対応）。誤登録の取り消しなど、例外は個別に決める。

## 3. 抜け道をふさぐルール

1. **全テーブルで RLS を有効にする**。ポリシーがないテーブルは誰も読めない状態になるので安全側に倒れる。マイグレーションのテストで「RLS が無効なテーブルが0件」を確認する。
2. **ビューは `security_invoker = true`**。付けないとビューの作成者権限で動き、RLS をすり抜けてしまう。
3. **`security definer` 関数**は `set search_path = ''` を付け、関数の最初で権限（`is_member()` など）と対象行を確認する。金額を返す関数はオーナー確認を必須にする。
4. **管理者が読めるテーブルに金額の列を足さない**。足したくなったら ★ テーブルに置く。
5. **集計の取得経路を分ける**。ホームの「今月の数字」はオーナー専用関数で取得し、管理者の画面ではその関数を呼ばない（呼んでも DB がエラーを返す）。
6. **サービスキー（秘密キー）の用途を限定**する。使うのは「ユーザーの招待」と「無効化（ログイン停止）」だけ。サーバー側のコードでのみ読み込み、ブラウザに渡さない。普段のデータ取得はログイン中のユーザーの権限（RLS が効く）で行う。

## 4. ログイン

- **招待制**。Supabase の「新規登録を許可」をオフにし、オーナーが設定画面から招待したメールアドレスだけがログインできる。
- ログイン方法は **Google アカウント** と **メールのマジックリンク**。
  - Supabase 標準のメール送信は「プロジェクトのメンバー宛てにしか送れない・1時間に2通まで」の制限があるため、招待メールとマジックリンクには無料のメール送信サービス（Resend など）を設定する（[setup.md](../setup.md)）。
- **無効化したら即ログイン不可**:
  1. `app_users.is_active = false` → 次の画面操作から RLS がすべてのデータを拒否する（即時）
  2. 同時に Supabase の管理機能でそのユーザーを利用停止にし、ログイン状態を取り消す → 再ログインもできない
- ログインしていない人が管理画面を開いたらログイン画面へ移動させる（Next.js の proxy）。ただし本当の防御は RLS。

## 5. スタッフ用マイページ

### URL の鍵（トークン）

- URL の形: `https://（アプリのURL）/m/（鍵）`
- 鍵は暗号論的に安全な乱数 32 バイト（URL で使える文字で 43 文字）。推測は事実上不可能。
- 再発行すると古い鍵はその場で無効になる（`staff.mypage_token` を置き換える）。
- 稼働状態が「終了」のスタッフのマイページは開けない。

### データの取得・更新

マイページは**テーブルを直接読まない**。次のような DB 関数（`security definer`）を、ログインしていない利用者の権限で呼ぶ。各関数は最初に鍵を検証してスタッフを特定し、**そのスタッフの分だけ**を扱う。サービスキーは使わない（コードの不具合があっても他人のデータに届かない）。

| 関数（予定） | 内容 |
|---|---|
| `mypage_home(token)` | 名前、打診中の現場、確定した予定、報告待ちの件数 |
| `mypage_respond(token, assignment_id, 参加できる/できない)` | 回答。参加できるなら空きを確認して「確定」か「補欠」、できないなら「辞退」 |
| `mypage_report_get / mypage_report_save(token, assignment_id, …)` | 実績報告の表示・保存（稼働日〜7日後、未確定のときだけ） |
| `mypage_availability_get / save / submit(token, 月, …)` | 稼働可能日の表示・保存・提出 |
| `mypage_history(token)` | 過去の稼働と自分の獲得件数（確定 / 速報） |

- 返す項目は画面に必要なものだけ。**金額（日当・インセンティブ・支払額）は返さない**。交通費・経費は本人が申請した額だけ。
- 他のスタッフの名前や連絡先も返さない（同じ現場のメンバー表示は要件にないので出さない）。

### そのほかの守り

| 対策 | 内容 |
|---|---|
| レート制限 | 鍵ごと・IPごとにアクセス回数を数える（例: 1分60回、鍵の誤り10分20回まで）。超えたら少し待ってもらう表示 |
| 検索エンジン対策 | `noindex`、`robots.txt` で全体を拒否 |
| 鍵の漏れ対策 | マイページは `Referrer-Policy: no-referrer`（地図リンクなどを開いたときに URL が相手に渡らない）、`Cache-Control: no-store` |
| ホーム画面に追加 | マイページ用の PWA 設定は開始 URL に本人の鍵を含める（追加したアイコンから本人のページが開く） |

## 6. 変更履歴（監査ログ）

- 対象: 金額系の全テーブル（`rank_rates` を含む）、`assignments`（状態）、`report_items`・`reports`（速報・確定）、`expenses`（状態・金額）、`companies`（営業ステータス・次回アクション）、`staff_private`。
- DB のトリガーで「誰が（ユーザー or スタッフ）・いつ・どのテーブルのどの行を・変更前・変更後」を自動記録する。画面側の書き忘れが起きない。
- 閲覧はオーナーのみ（変更履歴画面）。実績の修正履歴だけは実績確認画面で管理者も見られる（金額を含まない）。

## 7. 自動テストで確かめること

| テスト | 方法 |
|---|---|
| 管理者が金額系テーブルを読めない | ローカルの Supabase にオーナー・管理者・未ログインの3種類でつなぎ、★ テーブルすべてで「0件」または「権限エラー」になることを確認（`tests/rls/`）。★ テーブルを追加したら必ずここに足す |
| 管理者の画面・API に金額が含まれない | seed に「目印になる金額」（例: 日当 17,345 円）を入れ、管理者でログインして全画面を開き、通信の中身に目印の金額や口座番号が1つも含まれないことを Playwright で確認 |
| RLS の付け忘れがない | 全テーブルの RLS が有効かを DB のカタログから確認するテスト |
| マイページで他人のデータに触れない | スタッフA の鍵で スタッフB のアサインに回答・報告しようとして拒否されることを確認 |
| 無効化したユーザーが読めない | 無効化直後の同じログイン状態でデータが0件になることを確認 |
